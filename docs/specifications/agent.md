# novnow 仕様書 — AI エージェント

## 15. AI エージェント

### 15.1 原則

> 「あなたの執筆計画の管理だけを AI にしてもらうことも、本文やプロットは全てあなたが書き AI にアイデアだけ量産してもらうことも、小説ひとつ丸ごと AI に作ってもらうことも、プログラムのように本文を予測補完し執筆を効率化することもできます。あなたは、あなたのするべきことをするだけです。」（README）

この思想を仕様に落とすと、**「AI に何を任せるか」を決めるのは人間であり、novnow はその決定を実現する装置である**、ということになる。
LLM の自律作業を否定するのではなく、**委ねる範囲を人間が設計し、いつでも変更できる形** で提供する。

#### 15.1.1 委譲レベル（delegation）

役割ごとに、ユーザーが **AI の自律度** を 4 段階で設定する。

| レベル | 意味 | エージェントの書き込み | 連鎖・次タスク | 人間の関与 |
|---|---|---|---|---|
| `off` | 人間がその役割を担う | しない（補完・検索のみ） | 起こさない | すべて人間 |
| `propose`（**既定**） | 提案役 | `agents/proposals/` への提案のみ | 起こせない | 起動・採否を人間が行う |
| `apply` | 自動適用 | 本文・プロットへ自動適用（before/after は `agents/proposals/` に必ず残す） | 起こせない | 起動は人間。適用の事後確認・差し戻しができる |
| `autonomous` | 自律 | 自動適用 | **起こせる**（次のタスク起動・エージェント間連鎖） | 停止・範囲の変更・上限の設定 |

> **次タスクの起票は integrator のみ**（決定事項。付録 A.8 と整合）。`autonomous` であっても
> integrator 以外の役割は他のタスクを起こせない。エージェント間の **メッセージ** の受け渡しは
> 同一スレッド内の役割どうしで自由（§15.6）。

設定は `project.json` の `agents.delegation`（全役割の既定。既定値 `"propose"`）と
`agents.roles.<role>`（役割ごとの上書き。`"off"` を含む）で行う（§4.5.1）。
UI からも `agent` ワークスペースの委譲パネル（§15.7.6）で確認・変更でき、
変更は監査ログ（§5.10.5）に `delegation_changed` として残る（MUST）。

README の 4 つの例は、この設定の組み合わせで表現できる。

| README の例 | 設定 |
|---|---|
| 執筆計画の管理だけを AI に任せる | `roles: { "integrator": "autonomous" }`（他は既定のまま） |
| 本文・プロットは自分で書き、アイデアだけ AI に量産させる | `roles: { "ideator": "apply", "writer": "off", "plotter": "off" }` |
| 小説ひとつ丸ごと AI に作ってもらう | `delegation: "autonomous"`（全役割） |
| 全く任せない | `delegation: "off"` または `agents.enabled: false` |
| プログラムのように本文を予測補完する | 委譲レベルとは別軸の執筆支援（§9.4.3・§9.7.3）。どのレベルでも使える |

#### 15.1.2 原則

v1 では次を MUST とする。

| # | 規範 |
|---|---|
| A1 | **委譲レベルは人間が設定する**。`agents.delegation` と `agents.roles` はユーザーの明示した値のみを取り、novnow が自ら書き換えることはない（MUST）。変更はすべて監査ログに残る |
| A2 | 委譲レベル `propose` では、エージェントは **ファイルを直接書き換えない**。出力は必ず `agents/proposals/` に入り、人間が採否を決める。`apply` / `autonomous` では自動適用するが、**適用の before/after 記録は必ず `agents/proposals/` に残す**（MUST） |
| A3 | エージェント同士の通信は `agents/threads/` に **可視化** される。`propose` では人間の承認なしに相手に渡らない。`autonomous` では同一スレッド内の受け渡しは自動で行われる（§15.6） |
| A4 | 送信されるコンテキストは **送信前に全文を人間が見られる**（ドライラン、§15.7.2） |
| A5 | LLM へのアクセスは **すべて MCP 経由**。novnow 本体にプロバイダ SDK を持たない |
| A6 | エージェント機能を完全に無効化（`project.json.agents.enabled = false`）しても、他の全機能が無損失で動く |
| A7 | 委譲レベル `propose` では、`state: fixed` の節は **提案対象外**（人間が書いた文章を承認なしに書き換える提案を作らない）。`apply` / `autonomous` では書き換えうるが、監査ログに `fixed_overwrite` として記録し、**ステータスバーに 1 行通知する**（MUST） |
| A8 | 自律レベルの **上限は人間が決める**。1 セッションあたりのタスク数・連鎖ホップ数・入力文字数の上限を `agents.limits` で設定でき（既定あり）、超えたら自動で停止して人間に知らせる（W095、MUST）。上限を外す設定もできるが、その場合も監査ログは残る |

### 15.2 役割（6 + 統合）

| role | 日本語 | 担当範囲 | 入力の中心 | 出力 |
|---|---|---|---|---|
| `plotter` | プロット | 1 節〜1 場面のプロット案 | 上位プロット・配役・伏線 | B 形式の節テキスト（`proposal.kind = plot-field`） |
| `writer` | 本文 | 1 節の本文 | 当該節プロット・前後節・有効モード・役割語 | C 形式の節テキスト（`section-text`） |
| `ideator` | アイデア | 発想の量産 | 章の `summary`・未回収伏線・アイデア一覧 | `ideas.md` 追記案（`idea`） |
| `researcher` | 資料検索 | 資料の収集と要約 | 節のプロット・不足情報の質問 | 資料 MD + index 追記案（`material`） |
| `stylist` | 文体チェック | 役割語・語尾・リズムの検査 | 当該節本文・役割語パターン・直近 5 節 | 指摘リスト（`section-text` の差分提案） |
| `logician` | 論理整合性 | 伏線・時系列・設定矛盾の検査 | 全体/章プロットの `summary` 群・当該話の全節・用語 range | 指摘リスト（提案 or メッセージ） |
| `integrator` | 統合 | 上記の結果を突き合わせ、次に何をするか決める | 各タスクの状態・診断 | **既定は人間**（`agents.integrator = "human"` は `roles.integrator = "off"` と同義）。委譲レベルを `autonomous` にすれば執筆計画の管理ごと AI に任せられる（§15.1.1） |

役割の **プロンプトは自由に書き換え可能**。既定 7 種に加え、ユーザー定義のロールを追加できる（§15.2.1）。
どの役割の出力も、委譲レベル（§15.1.1）に従って **提案として積まれるか、自動適用されるか** が決まる。

#### 15.2.1 カスタムロール

`prompts/custom/<role>.md` として定義し、`project.json` の `agents.custom_roles` に登録する（形式は §5.9.2）。

| 項目 | 規則（MUST） |
|---|---|
| 権限 | 既定 7 種と **完全に同じ**。委譲レベル（§15.1.1）も同じくユーザーが設定でき、その範囲で直接書込・自動連鎖もありうる。それ以上の権限（独自接続・プロジェクト外への書き込み）を持たない |
| 出力種別 | `proposal.kind` は `note`（自由テキストの指摘）に固定。本文・プロット・資料の差し替え提案は作れない。本文を書かせたい場合は既定の `writer` 役割を委譲すればよい（§15.1.1） |
| 理由 | 構造化された出力（B 形式の節など）を正しく生成できる保証が無いため、既定は人間が読んで判断できる指摘に固定する。これは v1 の安全側の既定であり、P5 の禁止ではない |
| コンテキスト | `context:` で 9 ブロックの部分集合を選ぶ。`project` と `constraints` は常に含まれる |
| UI | `agent` ワークスペースの役割リストに、既定 7 種の下に区切って並ぶ。アイコンや色で区別しない |
| 上限 | 16 ロール（E034） |

**カスタムロールの用途の例**（ドキュメントに載せる想定）

| ロール名 | 目的 | 絞ったコンテキスト |
|---|---|---|
| `weapon-advisor` | 武器・防具の時代考証 | `materials` と当該節本文だけ |
| `medical-check` | 医療描写の妥当性 | 当該節本文と `constraints` だけ |
| `name-consistency` | 異世界固有名詞の表記ゆれ | `lexicon` と当該話全文 |
| `emotion-arc` | 1 話の感情曲線の起伏 | `plot` と `outline` だけ（本文を送らない） |

最後の例が示すとおり、**本文を送らない役割を作れること** がこの機能の要点である。
「何を渡さないか」を決める装置として使う（§5.9.2）。

### 15.3 タスクモデル

委譲レベル `propose`（既定）:

```
          人間が作る              人間が押す           MCP            人間が決める
 [intent] ───────▶ Task(draft) ───────▶ ready ───▶ running ───▶ review ───▶ accepted
                        │                                           │          └─▶ rejected
                        └── ドライランで context を確認 ─────────────┘
```

委譲レベル `apply`:

```
 [intent] ─▶ Task(draft) ─▶ ready ─▶ running ─▶ applied（自動）─▶ review（事後・差し戻し可）
```

委譲レベル `autonomous`:

```
 [intent] ─▶ Task(draft) ─▶ ready ─▶ running ─▶ applied（自動）
                ▲                                    │ エージェントが次の Task を起こせる
                └────────────────────────────────────┘
```

- タスクの単位は **1 節**（P1）。場面・話単位のタスクは「節タスクの束」として生成される。
  `propose` / `apply` では実行は 1 件ずつ人間が押す。`autonomous` では前タスクの完了を引き金に
  次のタスクが自動で起動される（**起票できるのは integrator のみ**、上限は `agents.limits`、A8）。
- タスク ID は `T` + 4 桁連番（`agents/tasks/` 内で最大値 +1、再利用禁止）。`agents/results/` の番号も数える
  （タスクのファイルを消しても番号は戻らない。提案 `P` とスレッド `TH` も同じ規則）。
- `context-hash` を記録し、**実行後にコンテキスト元が変わっていたら** レビュー画面で「古いコンテキストに基づく提案」と表示する。
- 自動適用（`apply` / `autonomous`）でも適用記録は `agents/proposals/P####.md` に残り（A2）、
  監査ログ（§5.10.5）に `auto_applied` イベントが書かれる（MUST）。

### 15.4 コンテキスト設計

> 人間向け UI が「必要なコンテキストを参照ペインに出す」のと同じ材料を、同じ優先順位で、LLM 向けに整形したものを送る。
> **人間とエージェントで情報源と優先順位を一致させる**ことが設計目標である（MUST）。

#### 15.4.1 ContextPacket の構造（固定順）

送信本文は Markdown。ブロックの順序と見出しは固定（LLM 側のパース安定性のため）。

```md
# novnow context
scene: 01-04-02-03
role: writer
delegation: propose
generated_at: 2026-10-09T12:00:00+09:00

## 1 project
title / genre / 文体規約（prompts/_shared/style.md の内容）

## 2 outline
all: <当該章の summary 1 行>
chapter: <当該話の summary 1 行 + goal>

## 3 plot
scene: <当該場面のプロット全文（B 形式、フィールド含む）>
section: <当該節のプロット行と check>

## 4 target
current: <当該節の現在の本文（空なら "(未執筆)"）>
before: <直前 2 節の本文>
after: <直後 1 節の本文（あれば）>

## 5 cast
<有効モードのキャラのみ。name / mode / personality / emotion / role / role-language>

## 6 lexicon
<当該節に現れる用語の term と definition 1 行>

## 7 materials
<参照された資料の id / title / summary / 本文（予算内で切り詰め）>

## 8 constraints
<prompts/<role>.md の output セクション + 機械的制約（字数・禁止記号・アノテーション規約）>

## 9 history
<同一節に対する直近 3 件のタスクの採否と人間のコメント>
```

中身の細部:

- 9 つの見出しは**中身が無くても必ず出す**（外したブロックも見出しだけ残る）。ブロックの中は `ラベル: 値`
  （値が複数行なら `ラベル:` の次の行から）か、`- ` で始まる 1 件。
- `1 project`: `title`（`project.json` の `title`、空ならプロジェクトの名前）・`genre`（`project.json` に
  あれば）・`style`（`prompts/_shared/style.md` の H1 と `//` コメントを除いた本文）。
- `2 outline`: `all`・`chapter`・`goal`（当該話のブロックの `goal`）。
- `4 target`: `current` → `before <ID>`（遠い節から近い節へ）→ `after <ID>`。前後は §8.1 の節の並び（ファイル名の順
  → ファイルの中の順）。当該節が本文に無ければ、ID が小さい直前の 2 節と大きい直後の 1 節。
- `5 cast`: 当該節の本文（話者注釈と `'` 参照）と当該場面のプロットに出るキャラ。
- `6 lexicon`: 当該節の本文と当該節のプロットに出る用語を、出現回数の多い順に。
- `7 materials`: 当該節の本文と話プロットの `material:` が明示参照する資料（§6.6.1）。ideator には既存のアイデアの
  一覧（`ideas`）も入れる（重複させないため、付録 A.4）。
- `8 constraints`: `output`（`## output` の本文）・`contract`（`prompts/_shared/output-contract.md` の本文）・
  機械的制約（writer の字数、記法を使わないこと、当該節が確定済みならそのこと）。
- `9 history`: 同じ節の直近 3 タスクの `ID 役割 状態` と却下・差し戻しのコメント、宛先がこの役割の**届いた**
  メッセージ（§15.6）。integrator はプロジェクト全体の直近 10 タスクの `ID 役割 対象 状態（起動者）`。
- `context-hash`（§5.10.1）は `generated_at:` の行を除いた本文の SHA-256（`sha256:` ＋ 16 進）。
- LLM への要求は `systemPrompt` = `## system`（＋ `## refuse`）、メッセージ = `## task` → パケット → `## examples`。
  ドライランのファイル（§15.7.2）はパケットだけ。

#### 15.4.2 ブロック別の文字数予算（既定値・`prompts/*.md` の `max-chars` で上書き可）

単位は「文字」。日本語は概ね 1.6 文字/トークン。

| ブロック | writer | plotter | stylist | logician | researcher | ideator | integrator |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1 project | 400 | 400 | 800 | 300 | 200 | 300 | 300 |
| 2 outline | 300 | 1,200 | 0 | 1,600 | 300 | 800 | 1,200 |
| 3 plot | 1,200 | 2,000 | 400 | 2,000 | 600 | 800 | 600 |
| 4 target | 2,400 | 600 | 2,400 | 2,400 | 300 | 400 | 300 |
| 5 cast | 1,200 | 800 | 1,600 | 800 | 200 | 600 | 300 |
| 6 lexicon | 600 | 400 | 400 | 800 | 200 | 400 | 200 |
| 7 materials | 800 | 600 | 0 | 600 | 3,000 | 1,000 | 200 |
| 8 constraints | 600 | 600 | 600 | 600 | 600 | 600 | 600 |
| 9 history | 400 | 400 | 400 | 400 | 200 | 300 | 2,300 |
| **合計上限** | **7,900** | **7,000** | **6,600** | **9,500** | **5,600** | **5,200** | **6,000** |

integrator の列はで足した（統合に要るのはタスクの状態なので `9 history` を厚くする）。
`max-chars` は役割の**合計**を上書きし、各ブロックの予算は表の比率のまま伸び縮みする。文字数はブロックの本文
（見出しの行を除き、ラベルと改行を含む）を Unicode のスカラー値で数える。

`project.json.agents.max_chars_per_request`（既定 12,000）を超える場合は、超過分を §15.4.3 の順で削る。

#### 15.4.3 切り詰め順序（決定論・固定）

超過時、次の順に削る。各ブロック内では「末尾から」削り、削った旨を `…（n 文字省略）` と明記する。

1. `7 materials`（資料本文 → `summary` のみに縮退）
2. `9 history`
3. `4 target` の `after` → `before`（遠い節から）
4. `2 outline` の `all`
5. `6 lexicon`（出現回数の少ない語から）
6. `2 outline` の `chapter`
7. `3 plot` の場面全文 → 当該節のみ

**決して削らないもの（MUST）**: `5 cast`（有効モード）、`3 plot` の当該節、`8 constraints`、`1 project` の文体規約。
これらを削らないと「役割語が崩れる」「約束を破る」からである。

手順: まずブロックごとに予算まで削り（上の順位の順。同じ順位の中は「後ろから」）、それでも
`max_chars_per_request`（と合計）を超えていれば、全ブロックをまたいで同じ順に削る。`4 target` の `current` も
削らない。決して削らない部分だけで上限を超えるときは送れない（ドライランで赤、送信できない。§15.9）。
削った部分は全部削っても見出し（ラベル）と `…（n 文字省略）` が残る。

#### 15.4.4 モードとコンテキストの関係（指示 6 との接続）

`5 cast` には **有効モードの性格だけ** を入れる（人間の参照ペインと同じ）。
これはプロンプト長の削減であると同時に、**LLM に「今はこの人格である」と一意に伝える**ための設計である。
他モードの性格を入れると平均化された人物像になるため、禁止する（MUST）。

#### 15.4.5 4 段階構造とコンテキスト削減（指示 11 との接続）

- 本文を書くとき、全体プロットは `summary` 1 行しか入らない。章プロットも 1 行 + `goal`。
- これにより、長編でも本文 1 節あたりの入力は 8,000 字前後に収まる。
- 意味論的検索（「この伏線はどこで回収される？」）も、まず `all.txt` の章 `summary` を検索し、
  一致した章の `NN.txt` を検索し、一致した話の `NN-MM.txt` を検索する **段階的絞り込み** で行う（全文検索しない）。
  これが指示 11 の「4 段階に分岐させることで LLM のコンテキスト削減と意味論的検索の高速性を担保する」の実装方針である。

#### 15.4.4 参考例（指定した話の本文・プロット）の付与〔状態: 未実装・実装計画済み〕

- タスク起票時に「例（お手本）」として任意の章・話・場面・節の本文またはプロットを指定し、LLM へのコンテキストとして与えられるようにする。

### 15.5 プロンプト設計

#### 15.5.1 必要なプロンプトの一覧（既定で生成するもの）

| ファイル | 目的 | 外してはならない要素 |
|---|---|---|
| `prompts/_shared/style.md` | 作品共通の文体規約 | 人称・時制・地の文と台詞の比率・禁止表現・句読点の癖 |
| `prompts/_shared/output-contract.md` | 出力の形式契約（全役割が include） | 「本文だけを出す」「見出しを付けない」「アノテーション記法を勝手に使わない」「不明点は書かずに質問として返す」 |
| `prompts/writer.md` | 1 節の本文生成 | 有効モードへの忠実さ、役割語の遵守、前節との接続、`check` の充足、字数目安 |
| `prompts/plotter.md` | 1 節のプロット生成 | 上位 `goal` との整合、1 節 1 出来事、伏線の明示、`check` の言語化 |
| `prompts/ideator.md` | アイデア量産 | 「採用されない前提で量を出す」「既出との重複を避ける」「1 行 1 案」 |
| `prompts/researcher.md` | 資料収集と要約 | 出典必須、推測と事実の区別、`conditions` の提案、120 字 `summary` |
| `prompts/stylist.md` | 文体チェック | 「書き換えでなく指摘」「役割語の不一致を最優先」「作家の癖を矯正しない」 |
| `prompts/logician.md` | 論理整合性 | 伏線・時系列・設定の矛盾のみを見る、推測の度合いを明示 |
| `prompts/integrator.md` | 統合（任意） | 次にすべき 1 手を提案する。既定では人間がすべき 1 手で、自分では作業を進めない（委譲レベル `autonomous` では次のタスクの起票まで可、§15.1.1） |

#### 15.5.2 プロンプトに必ず含める共通の約束（既定テキストの要件）

1. **役割の境界**: 「あなたは〈役割〉だけを行う。他の役割の仕事（例: 本文担当がプロットを直す）をしてはならない」
2. **出力契約**: 出力は 1 種類のみ。前置き・謝辞・説明を書かない。
3. **不確実性の扱い**: 分からないことは創作で埋めず、`## question` セクションに質問として書く。
4. **改変禁止域（既定）**: 与えられた本文のうち `state: fixed` の部分は引用のみ可、改変案を出さない。
   これは既定プロンプトの約束であり、ユーザーはプロンプトを編集して変更できる（§15.5.4）。
   委譲レベル（A7）が `apply` / `autonomous` でも既定プロンプトはこの約束を守る。
5. **言語**: 出力は作品の言語（日本語）で。UI 言語とは独立。
6. **長さ**: 指定字数の ±20% 以内。
7. **記法**: novnow のアノテーション（`@`, `'`, `;`）は、**指示された場合のみ** 使う。本文生成では `「」` と地の文のみ。
8. **委譲レベルとの整合**: 出力は `{{delegation}}` の値と矛盾しないこと（`propose` なら提案として読まれる前提で書く。
   `autonomous` なら `## message` や次のタスクの起票を含めてよい）。実際の適用・連鎖は novnow が委譲レベルに従って判断する（§15.1.1）

#### 15.5.4 編集可能性と既定への復元（U-7）

**方針（確定）**: novnow は **プロンプトのバージョン管理を一切行わない**。
履歴・世代・差分・ロールバックの仕組みを持たない。版管理が要るなら Git を使う（§14.2.1 の導線）。
その代わり、**既定プロンプトはいつでも必ず復元できる** ことを保証する。

##### (1) 既定プロンプトの保管場所

既定プロンプトは **novnow バイナリに埋め込む**（`include_str!`）。これが「一切変更されない場所」である。

| 性質 | 内容 |
|---|---|
| 所在 | 実行ファイルの中。ディスク上にも、ユーザーのホームにも、プロジェクト外にも存在しない |
| 変更可能性 | **実行時に書き換える手段が存在しない**（MUST）。設定でも上書きできない |
| プロジェクト間共有 | 既定文面は全プロジェクトで同一。これは「プロンプトを共有する」ことには当たらない（§13.1 との整合は下記） |
| バージョン | novnow 本体のバージョンに従う。本体を更新すると既定文面も変わりうる |

**規則 10（プロジェクト外に出てよいのは履歴パスのみ。特例は §13.1.1）との整合**: 埋め込み既定は
**ファイルシステム上のどこにも存在しない** ため、規則 10 に抵触しない。
「プロジェクトごとにプロンプトを持つ」という指示 8 の要請も、
**実際に使われるのは常に `prompts/` 配下のファイルだけ** であることで満たされる（MUST）。
埋め込み既定は「生成元」であって「読み込み元」ではない。

##### (2) 生成と上書き

| 状況 | 動作（MUST） |
|---|---|
| `prompts/` が無い | 既定一式を書き出す。I050 で通知 |
| `prompts/writer.md` だけが無い | **その 1 ファイルだけ** 書き出す。他には触れない |
| ファイルが存在する | **何があっても上書きしない**。novnow 本体を更新しても上書きしない |
| ファイルが壊れている（必須セクション欠落） | 上書きせず E029 を出し、そのロールだけ実行不可にする（必須は `## system` と `## task`までは E030 と書いていたが、環境変数の未解決のコードと重なるので分けた） |

##### (3) 復元コマンド

| 操作 | 動作 |
|---|---|
| `>prompt reset <role>` | 1 ロールを既定に戻す |
| `>prompt reset all` | 全ロールを既定に戻す |
| 確認 | 実行前に **現行版と既定版を並べて表示**（左右 2 ペイン）。差分は色分けせず、2 つの全文をそのまま並べる |
| 退避 | **しない**（MUST）。`.bak-*` を作らない |
| 警告文 | 「現在の内容は失われます。元に戻せません。」と明示する |
| undo | **できない**（MUST）。できないことを確認画面に書く |

**なぜ退避を作らないか**: `.bak-20261009-214012/` のようなディレクトリが増え続けると、
それ自体が「novnow 独自のバージョン管理」になってしまう。
U-7 の裁定は「版管理は Git に丸投げする」である。中途半端な退避機構を持つと、
Git を使っているユーザーには二重で邪魔になり、使っていないユーザーには不完全な安心を与える。
**「確認を丁寧にする」ことで安全を担保し、「履歴を持つ」ことはしない**。

##### (4) 既定との差分の可視化

- `agent` ワークスペースのプロンプト一覧に、既定と異なるロールには `編集済` と 1 語だけ添える。
- `>prompt diff <role>` で現行版と既定版を並置表示する（読み取り専用）。
- これは **閲覧のみ**。部分的に戻す操作は提供しない（部分マージは版管理であり、Git の仕事）。

##### (5) その他

- `prompts/*.md` はユーザーがいつでも編集できる。外部エディタでの編集も歓迎する（§8.5 の外部変更検出が働く）。
- プロンプトはプロジェクト間で共有しない（MUST）。他プロジェクトからコピーしたい場合は、ユーザーがファイルをコピーする（novnow は導線を提供しない）。
- カスタムロール（§5.9.2）には既定が存在しないため、`>prompt reset` の対象外。

### 15.6 エージェント間通信

- 媒体は `agents/threads/TH*.md`（§5.10.4）。直接の関数呼び出しは存在しない（MUST）。
  エージェント間のやり取りはすべて **メッセージ** としてスレッドに残る。
- 送信フロー: エージェント A の出力に `## message` セクションがあれば、novnow はそれを **未承認メッセージ** としてスレッドに積む。
  委譲レベル `propose` では人間が承認して初めて、宛先エージェント B のタスク生成時に `9 history` ブロックへ載る（A3）。
- 委譲レベルが `autonomous` の役割どうしの同一スレッド内では、承認なしに相手へ渡る（A3）。
  連鎖の各ホップはスレッドと監査ログに記録され、`agents.limits.max_chain_hops`（既定 10）を超えると自動で止まる（A8）。
- メッセージ種別（固定）: `request` / `deliver` / `question` / `reject` / `note`。
- スレッドは節単位でまとまり、`review` ワークスペースと `agent` ワークスペースの両方から辿れる。

### 15.7 人間向け管制 UI（`agent` ワークスペース）

```
┌──────────────────────┬──────────────────────┬──────────────────────┬──────────────────────┐
│ ① タスク一覧          │ ② コンテキスト検査    │ ③ 結果レビュー        │ ④ 委譲レベル          │
│  draft / ready /      │  ContextPacket 全文   │  before / after 差分  │  役割ごとのレベル表示  │
│  running / review /   │  ブロック別文字数     │  採用 / 一部採用 /    │  変更・総停止        │
│  applied（自動適用）   │  予算バー・切り詰め表示│  却下 + コメント      │  （人間が握る、P5）   │
│  （節 ID と役割で表示）│                      │  事後の差し戻しも可   │                      │
└──────────────────────┴──────────────────────┴──────────────────────┴──────────────────────┘
```

操作: テキストの入力欄にフォーカスが無いとき、`←` / `→` で列を移り、`↑` / `↓` で列の中を選ぶ。
修飾キーなしの文字キーは、フォーカスのある列のものだけが効く（§9.8.4）。

| 列 | キー |
|---|---|
| ① タスク | `N` 新規（役割・対象・目的・コメント。対象が場面・話なら節ごとに作る）・`R` 実行・`X` 中止・`D` ドライラン・`Space` 選択・`Ctrl+A` 表示中の `ready` を全選択・`Shift+R` 選択をまとめて実行（確認あり）・`Enter` 結果レビューへ |
| ② コンテキスト | `Space` そのブロックを外す / 戻す（`draft` / `ready` のタスクだけ。`exclude:` に書く）・`D` ドライラン |
| ③ 結果レビュー | `A` 採用・`P` 一部採用（`↑` / `↓` で行、`Space` で選ぶ、`Enter` で適用、`Esc` でやめる）・`X` 却下（`applied` / `accepted` なら差し戻し。どちらもコメント必須）・`M` このタスクの未承認メッセージを承認 |
| ④ 委譲レベル | `1`〜`4`（§15.7.6） |

タスクの状態: `N` で `draft`、`R` で `ready`（実行待ちの列に入る）、走り始めると `running`。
`agents.enabled` が `false` のときは、このワークスペースは「エージェントは無効です」とだけ出す（他のワークスペースは
すべてそのまま使える、A6）。

#### 15.7.1 タスク一覧
- 行: `T0042  writer  01-04-02-03  review`。`state` 色分け（`applied` は自動適用済みを示す）。
- タスクの起動者（人間 / エージェント）も表示する。`autonomous` で自動起動されたタスクは `起動: agent` と出る（MUST）。
- `N` で新規タスク（役割と対象節を選ぶ）、`Enter` で詳細、`R` で実行、`X` で中止。

#### 15.7.2 コンテキスト検査（A4 の実装）
- 送信予定の ContextPacket を **そのまま全文表示**。ブロックごとに文字数と予算に対する比率をバーで示す。
- 切り詰められたブロックは折り畳み表示で「何が落ちたか」を見せる。
- ブロック単位で「このブロックを外す」トグルが可能（人間がコンテキストを設計する、という思想の実装）。
- `D` でドライラン（送信せずパケットだけを `agents/results/T####.dryrun.md` に保存）。

#### 15.7.3 結果レビュー
- 差分は行単位。`A` 採用 / `P` 一部採用（行選択）/ `X` 却下。却下時はコメント必須（次回の `9 history` に入るため）。
- 採用時の適用先はファイル。適用は通常の編集と同じ経路を通り、§8 の保存ステートマシンに乗る（undo 可能）。
- `apply` / `autonomous` で自動適用された提案もここに `applied` として並び、**差し戻し**（本文を `before` に戻す）ができる（MUST）。
  差し戻しも undo 可能で、監査ログに残る。
- 採用・却下は `agents/proposals/P####.md` の `status` に記録され、**履歴は消えない**。

#### 15.7.4 常時表示される稼働表示と停止手段
- 実行中はステータスバーに `⟳ T0042 writer`（複数実行中は `⟳ 3件`）を出す。クリックで一覧（agent ワークスペースの
  ① を開く）、そこから個別に中止。
- 自律レベルで動いている役割は `⟳ writer (自律)` のように **レベルも表示** する（MUST）。
- どの役割がどの委譲レベルで動いているかは、いつでも委譲パネル（§15.7.6）で確認できる。
- 当該セッションの累計: 呼び出し回数・入力文字数・出力文字数（コストはプロバイダ依存のため金額表示はしない）。
- `Ctrl+Shift+X`（agent ワークスペース）で **すべての自律タスクを停止** し、委譲レベルを `propose` に戻す「総停止」を持つ（MUST、P5）。コマンドパレットからも `>agent stop-all` で実行できる。

#### 15.7.5 並列実行（U-8）

**確定事項**: v1 でエージェントの並列実行を提供する。並列化するのは **実行だけ** であり、
**自律の度合いは委譲レベル（§15.1.1）が決める**。`propose` / `apply` ではエージェントは他のタスクを起こせない。
`autonomous` では起こせる（上限は `agents.limits`、A8）。

##### (1) 起動の形

| 項目 | 規則（MUST） |
|---|---|
| 選択 | タスク一覧で `Space` により複数選択。`Ctrl+A` で表示中の `ready` を全選択 |
| 実行 | `Shift+R` で **選択したものをまとめて実行**。これが「人間の明示操作 1 回」である |
| 禁止 | エージェントが別のタスクを起動できるのは、**integrator 役割の委譲レベルが `autonomous` のときだけ**（A1、MUST）。並列度を決めるのも人間と設定だけ |
| 自動起動 | integrator（`autonomous`）は、前タスクの完了を引き金に次のタスクを自ら起こせる。起こされたタスクは `起動: agent` と記録され、`agents.limits.max_tasks_per_session` で止まる |
| 確認 | 実行前に「n 件のタスクを実行します / 合計入力 m 文字 / 使用サーバ一覧」を出して確認を取る |
| ドライラン | 複数選択したままドライランもできる。全パケットが `agents/results/*.dryrun.md` に出る |

##### (2) 並列度の制御

| 項目 | 規則 |
|---|---|
| 設定 | `project.json` の `agents.max_parallel`（既定 **2**、範囲 1–8） |
| 既定が 2 である理由 | 「少し速い」程度に留め、結果を人間が読める速度を超えさせないため。1 では並列の意味が無く、大きすぎるとレビュー待ちの山ができる |
| キュー | 選択したタスクは FIFO のキューに入り、`max_parallel` 件ずつ走る |
| サーバ別上限 | 同一 MCP サーバへの同時接続は **最大 2**（MUST）。`max_parallel` がそれより大きくても、サーバごとには 2 を超えない |
| `max_parallel = 1` | 完全に逐次。v0 相当の挙動 |

##### (3) 競合の排除（MUST）

| 規則 | 内容 |
|---|---|
| R1 | **同一 SceneId を対象とするタスクは同時に走らせない**。キューで後続を待たせる |
| R2 | 同一 role × 同一 scene のタスクは、そもそも 2 件作れない（作成時に E035） |
| R3 | 提案ファイル（`P####.md`）の採番は **採番ロックを取って逐次に行う**。並列でも ID は衝突しない |
| R4 | `materials/index.json` の `next_id` も同様にロックする |
| R5 | `propose` では出力は常に `agents/proposals/` に入り、**本文ファイルへの並列書き込みは原理的に起こらない**（A2 の帰結）。`apply` / `autonomous` では自動適用が本文を書き換えるが、適用は R6 の逐次キューで処理される |
| R6 | 本文への適用（人間の採用でも自動適用でも）は **常に逐次** で行う（MUST）。ここを並列化してはならない。自動適用はキューに入り 1 件ずつ適用され、すべて監査ログに残る |

##### (4) 表示

```
実行中  ⟳ 2 / 待機 3 / 完了 4
  ⟳ T0042  writer    01-04-02-03   12秒
  ⟳ T0043  stylist   01-04-02-04    8秒
  ·  T0044  writer    01-04-02-05   待機
  ·  T0045  logician  01-04         待機
  ✓  T0039  plotter   01-05-01-01   レビュー待ち
```

- 完了したものから順に「レビュー待ち」に積まれる。**完了順にポップアップを出さない**（MUST。執筆の邪魔になる）。
- レビューは人間が好きなときに `agent` ワークスペースで行う。
- 1 件失敗しても他は続行する。失敗したタスクは `ready` に戻り、**自動再試行はしない**（どの委譲レベルでも、MUST）。
- 全件完了時にステータスバーの件数が変わるだけで、音も通知も出さない。

##### (5) 並列化しても変わらないこと

- コンテキストは **タスクごとに独立** に構築される。タスク間でコンテキストを共有・引き継ぎしない（MUST）。
- `propose` / `apply` ではタスク間でメッセージを自動的にやり取りしない（A3、MUST）。
- 「writer の結果を stylist に自動で渡す」ようなパイプラインは `propose` / `apply` では **作られない**（MUST）。
  `autonomous` ではユーザーが委ねた範囲でのみ連鎖が起き、各ホップはスレッドと監査ログに記録され、いつでも止められる（A8）。
  並列実行は「独立した作業を同時に始める」ことであり、**自律の度合いは委譲レベルが決める**（§15.1.1）。

#### 15.7.6 委譲パネル（P5 の実装・レイアウト図の ④）

- 役割ごとの現在の委譲レベルを一覧表示する（`off` / `propose` / `apply` / `autonomous`）。
- 役割行にフォーカスがあるとき `1` / `2` / `3` / `4` を押すと、その役割のレベルを `off` / `propose` / `apply` / `autonomous` に変更する（MUST。§9.8.4 の衝突確認どおり、修飾キーなしの数字キーは他の割当と衝突しない）。
- コマンドパレット（`Ctrl+P`）からも `>agent delegation <role> <level>` で変更でき、`>agent stop-all` で総停止できる（MUST）。
- 変更は `project.json` に保存され、監査ログ（§5.10.5）に `delegation_changed` として残る（MUST）。
- README の使い方（「計画の管理だけ AI に任せる」「この役割だけ止める」等）が、このパネルだけで完結する（MUST）。
- レベル変更は実行中のタスクには影響しない（実行中のタスクはその時点のレベルで最後まで動く）。
  停止したいときは総停止（§15.7.4）を使う。

#### 15.7.7 `agents/mcp.json` 編集モーダルと参考例指定 UI〔状態: 未実装・実装計画済み〕

- コマンドパレットおよび `agent` ワークスペースから、`agents/mcp.json` をアプリ内で編集・保存するモーダルへ移行できる。
- タスク起票フォームで、LLM に「例」として渡す話の本文またはプロットの範囲を指定できる。

### 15.8 MCP

#### 15.8.1 クライアントとして（novnow → LLM）
- `agents/mcp.json`（§5.11）に定義されたサーバへ stdio で接続。
- 役割 → サーバの割り当ては `roles` フィールド。複数一致時は定義順の先頭。
- 呼び出しは MCP の `sampling`（モデル生成）または、サーバが公開する `tools` のうち許可されたもの（`allow_tools`）。
- タイムアウト（既定 60s）・**1 タスク 1 呼び出し**（連鎖は新しいタスクとして起こる、§15.3）・キャンセル可能。
- サーバが落ちている場合は E063 を出し、タスクは `ready` のまま残す（自動再試行しない）。

#### 15.8.2 Web 版での扱い
- ブラウザから stdio の MCP サーバは起動できない。Web 版では:
  - `transport: "http"` のサーバのみ利用可能（CORS 設定はユーザー責任）。
  - 設定が無い場合、`agent` ワークスペースは「この環境では LLM 呼び出しができない」旨を表示し、
    **タスク作成とドライランは可能**（コンテキスト設計は人間の作業なので、LLM なしでも価値がある）。
  - v1 の Web 版は `http` の MCP を持たない（常に「この環境では LLM 呼び出しができない」）。

#### 15.8.3 サーバとして（外部エージェント → novnow）

`novnow mcp <dir>` で MCP サーバとして起動し、外部の AI クライアントにプロジェクトのドメイン API を公開する。
**公開するのは core の純粋関数のみ**（§3）であり、UI を経由しない。

| ツール名 | 引数 | 動作 | 書き込み |
|---|---|---|---|
| `novnow.project.info` | — | タイトル・構造・統計 | なし |
| `novnow.structure.tree` | `level` | 章/話/場面/節のツリーと `summary` | なし |
| `novnow.plot.get` | `scene`, `level` | 指定レベルのプロット | なし |
| `novnow.section.get` | `scene`, `neighbors` | 本文と前後節 | なし |
| `novnow.cast.get` | `scene` | **有効モードのみ** の配役 | なし |
| `novnow.lexicon.search` | `query` | 用語検索 | なし |
| `novnow.materials.search` | `query`, `category`, `scope` | 資料検索（§16.3） | なし |
| `novnow.context.build` | `role`, `scene` | ContextPacket をそのまま返す | なし |
| `novnow.diagnostics.run` | `scope` | 診断一覧 | なし |
| `novnow.section.propose` | `scene`, `text`, `note` | **提案を作る**（本文は書き換えない） | `agents/proposals/` |
| `novnow.section.write` | `role`, `scene`, `text`, `note` | 本文を直接書き換える。**`role`（呼び出し役割）は必須**で、その役割の委譲レベルが `apply` / `autonomous` のときのみ書き込める（それ未満または省略時は E036） | `contents/`（記録は `agents/proposals/`） |
| `novnow.plot.write` | `role`, `scene`, `level`, `text` | プロットを直接書き換える。**`role`（呼び出し役割）は必須**で、その役割の委譲レベルが `apply` / `autonomous` のときのみ書き込める（それ未満または省略時は E036） | `plots/`（記録は `agents/proposals/`） |
| `novnow.materials.propose` | `title`, `source`, `markdown`, … | 資料を `status: proposed` で追加 | `materials/inbox/`, `index.json` |
| `novnow.mail.send` | `to`, `kind`, `scope`, `body` | 未承認メッセージを積む | `agents/threads/` |

- 書き込み系ツールは **呼び出し役割の委譲レベル（§15.1.1）に従う**。`propose` では必ず提案のみ（A2）。
  外部クライアントはツールの `role` 引数で呼び出し役割を指定し、その役割の委譲レベルが
  `apply` / `autonomous` のときのみ `novnow.section.write` / `novnow.plot.write` で直接書き込める。
- 直接書き換えが本文・プロットを変更しても、**変更前の状態は `agents/proposals/` に記録され**（A2）、
  監査ログに `direct_write` が書かれる（MUST）。
- サーバモードでも規則 10 は有効（書き込みはプロジェクト内のみ）。委譲レベルに関わらず規則 10 を超える権限は持たない（MUST）。
- 細部: 呼び出しのたびにプロジェクトを読み直す。結果は JSON のテキスト 1 つ、失敗は `isError: true` と
  文言（E036 などの診断の文言）。`scene` は 4 階層の構造 ID。`novnow.plot.write` の `level` は `episode`（話プロットの節）
  だけ。直接書き込みも自動適用と同じ検証を通し、E 系の診断が増えるなら書かずに `open` の提案として残して失敗を返す。
  `novnow.mail.send` の送り手は `mcp`。`novnow.materials.propose` の `added_by` は `agent:<role>`（`role` 引数が無ければ
  `agent:mcp`）。起動時に `prompts/` の欠けた既定ファイルを書き出す（§15.5.4。`novnow check` は書かない）。

#### 15.8.4 ローカル LLM 簡易モード

API キーを持たないユーザーが、ローカルで動く LLM をすぐ使えるようにする。

##### (1) 設計上の位置づけ（MUST）

**これは MCP の迂回路ではない。** 原則 A5（LLM へのアクセスはすべて MCP 経由）は変わらない。
簡易モードが行うのは、**`agents/mcp.json` を人間に代わって 1 件分だけ書く** ことである。
生成されたサーバ定義は普通の MCP サーバ定義であり、あとから自由に編集できる。

```
[設定画面で URL を入れる] → agents/mcp.json に local サーバを 1 件書く → 以降は通常の MCP 経路
```

novnow 本体が HTTP で LLM API を直接叩くコードを持つことは **禁止**（MUST）。
LLM プロバイダ固有の SDK や OpenAI 互換クライアントを同梱せず、すべての LLM 通信を MCP に限定する（MUST）。

##### (2) 設定

`project.json` の `agents.local_llm`:

```json
{ "enabled": true, "url": "http://localhost:11434", "model": "qwen2.5:14b" }
```

| キー | 既定 | 意味 |
|---|---|---|
| `enabled` | `false` | 簡易モードを使うか |
| `url` | `"http://localhost:11434"` | ローカル LLM のエンドポイント。Ollama の既定ポート |
| `model` | `""` | モデル名。空なら接続時に取得した一覧の先頭 |

##### (3) 設定 UI

`agent` ワークスペースの「ローカル LLM」セクション（3 行だけ）。

```
ローカル LLM     ☐ 使う
URL              http://localhost:11434
モデル           qwen2.5:14b        [接続を確認]
```

| 操作 | 動作 |
|---|---|
| `[接続を確認]` | エンドポイントへ 1 回だけ問い合わせ、応答すればモデル一覧をプルダウンに入れる |
| 成功 | `agents/mcp.json` に `local` サーバを追記（既にあれば更新）。I057 で通知 |
| 失敗 | **E064**。原因（接続拒否 / タイムアウト / 応答が解釈できない）を 1 行で出す |
| タイムアウト | 3 秒（MUST。ローカル前提なので短くてよい） |
| 自動検出 | **しない**（MUST）。ポートスキャンや既知ポートの総当たりは行わない。URL は人間が入れる |

##### (4) 生成される `agents/mcp.json` の断片

```json
{
  "servers": {
    "local": {
      "transport": "http",
      "url": "http://localhost:11434",
      "roles": ["*"],
      "model": "qwen2.5:14b",
      "managed_by": "novnow-local-llm"
    }
  }
}
```

- `managed_by` が付いたサーバだけを簡易モードが上書きする（MUST）。
  手で書いたサーバ定義には絶対に触れない。
- ユーザーが `managed_by` を消せば、以後は手動管理のサーバとして扱われる。

##### (5) 制約と明示

| 項目 | 規則 |
|---|---|
| 接続先 | **localhost / 127.0.0.1 / ::1 のみ**（MUST）。外部ホストの URL は拒否して E064。外部 API を使うなら通常の MCP 設定を書く |
| Web 版 | ブラウザから localhost への接続は混在コンテンツ・CORS の制約を受ける。使えない場合は理由を 1 行で表示し、機能を隠す |
| 品質 | 「ローカル LLM は出力品質が既定プロンプトの想定より低い場合があります」と設定画面に 1 行だけ書く。評価や推奨モデルの提示はしない |
| 並列 | §15.7.5 のサーバ別上限（同時 2）が適用される。ローカルマシンの負荷を考えると既定のままが安全である旨を 1 行添える |

### 15.9 失敗モードと安全装置

| 事象 | 挙動 |
|---|---|
| LLM が形式を守らない（前置きを書く等） | 採用時に自動整形しない。レビュー画面で「契約違反」を警告表示し、人間が整える |
| LLM が `state: fixed` を書き換える提案を返した（`propose`） | 提案を `superseded` にせず、警告付きで表示。採用ボタンに確認を 1 段挟む |
| 自動適用（`apply` / `autonomous`）が構文エラー（E 系）を生む | 自動適用の前に §7 の検証を行い、エラーを生む適用は **行わずに提案として残す**（MUST） |
| 自律タスクがセッション上限（`agents.limits`）に達した | 自動で停止し、W095 で人間に知らせる。それまでの適用は残る |
| 自律の連鎖がホップ上限（`max_chain_hops`）を超えた | 連鎖を止め、最後のタスクの結果だけを残す |
| 自動適用が `state: fixed` の節を書き換えた | 監査ログに `fixed_overwrite` を記録し、ステータスバーに 1 行通知する（例: `fixed を書き換えました: T0042 → 01-04-02-03`）（MUST） |
| コンテキストが予算を超え続ける | ドライランで赤表示。送信ボタンを無効化し、ブロックを外すよう促す |
| MCP サーバが大量のトークンを返す | 出力 20,000 字で打ち切り、`truncated: true` を記録 |
| 同じ節に対する提案が複数 | 併置して比較表示。採用すると他は `superseded` |
| ネットワーク断・プロセス異常終了 | タスクは `ready` に戻る。部分出力は破棄（中途半端な提案を作らない） |

## 付録 A: 既定プロンプトの要件

各プロンプトに **必ず書かれていなければならない内容** を列挙する。文面は実装時に起こす。

### A.1 `_shared/output-contract.md`（全役割が参照）
1. 出力は指定された 1 種類のみ。前置き・要約・謝辞・自己言及を書かない。
2. Markdown の見出しやコードブロックで包まない（求められた場合を除く）。
3. 入力に無い固有名詞を作らない。必要なら `## question` に質問として書く。
4. 字数指定は ±20% 以内。
5. novnow の記法（`@` / `'` / `;`）は指示があるときだけ使う。
6. 既存文の改変提案は、変更箇所を最小にする。
7. 不確実な事実は「不確実である」と明示する。

### A.2 `writer.md`
- 有効モードの `personality` / `emotion` に沿った内面描写をすること。
- `role_language` のパターンに沿う台詞にすること。**パターンに無い語尾を発明しない**。
- 直前の節の末尾から自然に続くこと。直後の節が与えられている場合はそこへ接続できること。
- `check` に書かれた条件をすべて満たすこと。満たせない場合は本文を書かず質問を返すこと。
- 説明的な地の文で心情を断定しない（「〜と思った」の多用を避ける）という作品側の文体規約を参照すること。

### A.3 `plotter.md`
- 1 節 = 1 出来事。2 つ以上の出来事を 1 節に入れない。
- 親（章）プロットの `goal` に対する貢献を 1 文で述べられること。
- 伏線を張る場合は `seed`、回収する場合は `payoff` を明記すること。
- 本文を書かない（台詞を書かない）こと。

### A.4 `ideator.md`
- 1 行 1 案、最大 20 案。採用率が低い前提で量を出す。
- 既存の `ideas.md` と重複しないこと（入力に既存一覧が与えられる）。
- 作品のジャンル・トーンから外れた案も 2 割程度混ぜること（発想の幅のため）。

### A.5 `researcher.md`
- 出典（URL または取材メモの出所）が無い情報を書かない。
- 事実・推測・一般論を段落で分けること。
- 120 字以内の `summary` と、`conditions`（いつ必要になるか）の案を必ず付けること。
- 小説本文に使える形に加工しない（素材のまま渡す）。

### A.6 `stylist.md`
- **書き換えない。指摘する。** 指摘は「位置・該当文字列・理由・改善案」の 4 点セット。
- 役割語の不一致を最優先に検出する。
- 作家固有の癖（句読点の打ち方、体言止めの多用など）を矯正しない。`_shared/style.md` に書かれた規約違反のみを指摘する。

### A.7 `logician.md`
- 伏線（`seed`/`payoff`）、時系列、設定（用語の `range`、キャラのモード範囲）の矛盾のみを見る。
- 物語の良し悪しを評価しない。
- 指摘には「確実な矛盾 / 疑わしい点 / 情報不足で判断不能」の 3 段階を付ける。

### A.8 `integrator.md`（任意）
- 次にすべき 1 手を提案する（既定では **人間が** すべき 1 手）。
- 自分で作業を進めない。他エージェントを起動する指示を出さない（既定では人間が押す）。
  委譲レベルが `autonomous` のときは、次のタスクの起票まで行ってよい（§15.1.1）。
- 現在の停滞理由（どのタスクが止まっているか）を 1 文で述べる。
