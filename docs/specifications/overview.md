# novnow 仕様書 — 概要・原則・処理モデル

## 1. 設計原則

README に現れる作者の思想を、実装判断に使える規則へ落としたもの。迷ったらこの章に戻る。

### P1. 1 節が世界の単位である
IDE のあらゆる機能（表示・保存・診断・AI タスク・エクスポート範囲・検索結果）は **節（SceneId の第 4 階層）** を既定の単位とする。
節より大きい単位を扱う機能は、必ず「節の集合」として実装する。

### P2. ワーキングメモリを IDE が肩代わりする
人間が覚えていなくてよいものは画面に出す。出すものは「今の節に必要なもの」だけに絞る。
→ モードの性格は **有効なモードだけ** 表示する（他モードは隠す）。用語は **今の節に出現するもの** を先頭に置く。

### P3. キーボードで完結する
マウス操作は常に代替キーボード操作を持つ（MUST）。
逆に、**キーボードだけで到達できない機能を作ってはならない**。

### P4. 決定論
同じ入力からは常に同じ表示・同じ診断・同じコンテキストが得られる。
曖昧検索のスコアリング、辞書一致、コンテキスト切り詰めは、すべて順序まで決定論的に定義する（§6.2, §16.3, §15.4）。

診断や分かち書きに使う部品は、実行時に乱数を必要としないものに限る（「確率・統計モデル」とは実行時に乱数を必要とするものを指す）。学習済みの部品を使う場合でも、中身を人間が把握できる規模の小さな固定モデルだけを許容し、全員へ同じ学習結果を配布する。実行中に学習して人ごとに変わる部品は持たない。

### P5. AI に何を任せるかは人間が決め、その範囲で AI は自律に動く
README の明文に従う。LLM による自律作業は **一切否定しない**。執筆計画の管理だけを AI に任せることも、
本文やプロットは自分で書いてアイデアだけを AI に量産させることも、小説ひとつ丸ごとを AI に作らせることも、
**全く任せない** ことも、すべてできる。この思想の核心は **「LLM に何を任せ、何を人間がするか」をユーザーが指定できること** であり、
人間の創作性は「AI を使わないこと」で担保するのではなく、**任せる範囲を自分で決め、その結果に責任を持てること** で担保する。
「あなたは、あなたのするべきことをするだけ」である。

したがって:

- **委譲レベル（delegation）** — 役割ごとに「どこまで AI を自律させるか」をユーザーが設定する（MUST、§15.1.1）。
  既定は安全側（提案のみ・人間が採否）だが、ユーザーはいつでも全委譲（直接書込・連鎖・自律実行）に切り替えられる（MUST）。
- novnow が **ユーザーの設定なしに** 委譲範囲を広げることはない（MUST）。範囲の変更はすべて監査ログ（§5.10.5）に残る。
- 自律させた場合でも、**上限（タスク数・連鎖数・文字数）と停止手段は必ず人間が握る**（MUST、§15.1.1 A8、§15.7.4）。
  創作性の担保は禁止ではなく、**「止められること・戻せること・いつでも見られること」** で行う。

### P6. プロジェクトは自己完結する
プロジェクトディレクトリをコピーすれば、プロンプトも資料も設定も丸ごと移動する。
プロジェクト外に出てよい情報は **プロジェクトディレクトリパスの履歴のみ**（§13.1）。
例外は、ユーザーが書き出し先を明示したエクスポートと、配布物の取得専用領域に限定する（§13.1.1）。

### P7. ドメインは UI を知らない
小説管理のドメインロジックは特定の画面フレームワークやストレージ実装に依存しない純粋な規則として定義する（§3）。

## 2. 用語

### 2.1 用語定義

| 用語 | 定義 |
|---|---|
| 章 (chapter) | 構造の第 1 階層。`A` |
| 話 (episode) | 第 2 階層。`B`。本文 1 ファイル = 1 話 |
| 場面 (scene) | 第 3 階層。`C`。本文中の `@A-B-C` 見出しで始まる |
| 節 (section) | 第 4 階層。`D`。場面内を `;` 行で区切った単位。**編集・保存・AI タスクの基本単位** |
| SceneId | `A-B-C-D` の 4 階層 ID。`01-04-02-03` |
| PartialSceneId | 先頭から 1〜4 階層を指定した ID。`01`, `01-04`, `01-04-02` |
| 範囲式 (RangeExpr) | `@01-04 .. @02-01` のような PartialSceneId の閉区間 |
| 辞書 (dictionary) | `'` で参照できる名前空間の総称。キャラ・別名・用語・資料 ID・資料タイトルを含む |
| 参照 (reference) | 本文・プロット中の `'名前` / `@01-04-02` / `@キャラ名` といった解決対象トークン |
| モード (mode) | キャラの性格の切替単位。`characters.md` で定義し、プロットで節/場面に割り当てる（§6.4） |
| 役割語 (role language) | キャラらしさを担う語尾・言い回し。`characters.md` にパターンとして定義し、本文中の一致に緑下線を引く（§6.5） |
| 資料 (material) | 取材・参考文献。`materials/index.json` で採番し、本体は MD で保存する（§5.8） |
| ワークスペース (workspace) | 用途別 UI の単位。本文執筆・話プロット・読者 など 9 種（§10） |
| 参照ペイン | 現在の節に必要な情報を出すペイン。既定は画面右 |
| 文脈ビュー | 前後の節を読むための読み取り専用ビュー（§9.3） |
| 提案 (proposal) | エージェントや MCP クライアントが作る変更案。委譲レベル `propose` では未採用のまま積まれ人間が採否を決める（§15.1.1、§15.3） |
| 委譲レベル (delegation) | 役割ごとにユーザーが設定する AI の自律度。`off` / `propose` / `apply` / `autonomous` の 4 段階（§15.1.1） |

## 3. アーキテクチャと処理モデル

### 3.1 層と責務の分離

novnow は「ドメイン規則」「入出力境界」「環境固有の入出力」「ユーザーインターフェース」の 4 つの責務を厳格に分離する。
小説管理のドメイン規則は画面表示やストレージの種別（デスクトップのファイルシステム / Web のブラウザ内ストレージ）に依存せず、同一の入力に対して常に同一の解析結果・診断・コンテキスト・エクスポート出力を返す（MUST）。

### 3.2 ドメイン純粋性と外部隔離規則

ドメイン処理は次の外部要素に一切依存してはならない（MUST）。

- 画面フレームワーク・ダイアログ・クリップボード
- ファイルシステム・ネットワーク・サブプロセスなどの直接入出力
- ブラウザ API・OS 固有 API
- スレッド・非同期ランタイム
- グローバルな現在時刻・乱数

文字の正規化（NFKC）やパターン照合はすべて純粋な決定論的変換として定義し、実行環境や OS ロケールによって結果が変化してはならない（MUST）。

### 3.3 機能構成

novnow の機能は以下の 8 つの領域で構成される。

| 領域 | 役割 |
|---|---|
| 構造 ID・テキスト基盤 | 4 階層構造 ID（`A-B-C-D`）・範囲式・行単位字句解析・位置変換・インクリメンタル再解析 |
| 構文解析 | 本文（C 形式）・全体/章プロット（A 形式）・話プロット（B 形式）・キャラクター・用語・アイデア・資料索引・プロンプト・プロジェクト設定の解析と無損失往復変換 |
| 意味解決 | 辞書トライ構築・`'` の最短一致・セマンティックトークン・モード解決・役割語照合・資料 ID 解決・参照ペイン優先順位 |
| 診断と支援機能 | 77 種の診断コード判定・補完・ホバー・インレイヒント・クイックフィックス・定義移動・参照検索・構造シンボル・整形・一括改名・折りたたみ |
| ストレージ規則 | プロジェクト外書き込み禁止（規則 10）・パス履歴管理・Zip アーカイブ選別・外部変更検知 |
| エクスポート・読者表示 | アノテーション除去パイプライン・範囲抽出・縦書き組版計算 |
| AI エージェント基盤 | コンテキスト 9 セクション構築・トークン予算切り詰め・タスク/提案/スレッド管理・MCP 連携・安全装置 |
| シェル・ワークスペース・CLI | 共通シェル・9 ワークスペース・2 言語カタログ・テーマ配色・CLI サブコマンド |

### 3.4 言語機能サービス（LSP 相当機能）

エディタおよび各ワークスペースが提供する言語支援機能は、対象文書・位置（または範囲）・プロジェクト状態のみから決定論的に算出される以下の 12 機能で構成される（MUST）。

| 機能 | 役割 | 主な画面用途 |
|---|---|---|
| セマンティックトークン | 行内の構文要素の種別分類 | 構文ハイライト（§11.2） |
| 補完 | カーソル位置に応じた候補提示 | `'` 補完・モード補完・資料 ID 補完（§9.7.3） |
| ホバー | 参照トークンの解決先情報の取得 | 参照トークンの詳細表示 |
| インレイヒント | 参照トークン直後の補助表示 | 資料タイトル・モード名の薄表示（§6.6） |
| 文書診断 | 構文・意味・整合・執筆支援の検査 | 波線表示・`review` ワークスペース（§7） |
| コードアクション | 診断に対する修正候補の生成 | `Ctrl+.` クイックフィックス（§7） |
| 定義移動 | 参照トークンから定義箇所への解決 | `'名前` から `characters.md` / `words.md` / 資料への移動 |
| 参照箇所検索 | 項目を使用している全箇所の列挙 | 「このキャラ・用語・資料を使っている節」の一覧 |
| 文書シンボル | 見出し階層の抽出 | 構造ツリー・ジャンプパレット |
| 文書整形 | 正規化規則に基づくテキスト整形 | `>format` による正規化（§5.12） |
| 一括改名 | 定義と全参照の一括名称変更 | キャラクター名・用語の一括改名 |
| 折りたたみ範囲 | 階層ブロックの範囲算出 | `plot-outline` の構成ツリーの章→話展開（§10.3.1） |

**位置表現**: 文書内の位置は UTF-8 バイトオフセット・文字インデックス・UTF-16 コード単位の相互変換を一貫して扱う（MUST）。

参照ペイン（§9.5）に並ぶ行は、表示する文字列だけでなく、対応する移動先（文書と位置）または開く対象をあわせて返す。画面と外部インターフェース（§19）は同じ返却値を共有する。

### 3.5 状態フロー（1 キーストロークの流れ）

```
打鍵入力
  → 編集行のみの再字句解析・再トークン化（O(編集行)）
  → 未保存状態への遷移（§8.2 自動保存ステートマシン）
  → 参照ペインの再構築（デバウンス 80ms、§9.5）
  → 画面再描画
```

画面更新を伴う処理は **1 フレーム 8ms 以内** に収める（§18）。それを超える処理（プロジェクト全文検索・エクスポート・MCP 呼び出し）はバックグラウンドで実行し、進捗をステータスバーに表示する。
