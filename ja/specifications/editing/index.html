8. 編集モデルと保存

8.1 節単位編集

  • 編集対象は常に 1 つの節。節エディタ（§9.4）は複数行の TextEdit で、節のテキスト全体を保持する。
  • 「編集中の節」は文脈ビューでは本文を表示せず、編集中であることを示すプレースホルダのみを置く（§9.3.2、指示 3）。
  • 節の移動（Alt+↑ / Alt+↓ / ジャンプ / クリック）で、編集中の節は即座に文書へ反映され、保存がトリガーされる。

8.1.1 節の分割

  • 節の分割は、カーソルのバイト位置（文字境界）で現在の節を 2 つに分ける。話者注釈・参照・ルビ等の途中でも、安全な位置へ寄せたりはしない。分割で壊れた記法が生じた場合は、通常の診断・表示規則に従う。
  • カーソルが節の途中にあるときは、現在節と既存の次節の間に下側の新しい節を挿入する。カーソルが節先頭にあるときは何もしない。節末尾では既存の次節へ移り、無ければ作る（従来の「確定して次の節へ」と等価）。
  • 何も書かれていない節では、新たな空節を作らない。「何も書かれていない」は空の節の診断（W012）と同じく、内容行が無い節または空白行だけの節を指す。行コメントは内容として数える。

8.1.2 節の削除

  • 節の削除は、どの入口（文脈ビューのボタン・プロット一覧のボタン・ショートカット・コマンドパレット・ヘッドレス操作）から行っても、本文の対象節と対応するプロットの節ブロックを一緒に削除する意味に統一する。対応するプロットブロックが一意に定まらない場合は、何も削除せずその旨を知らせる。
  • 削除すると後続の節番号は繰り上がる。節番号は位置から決まる（§5.2.2）ため、プロットのモード割当や提案・タスクの対象節も位置に従って対応する。
  • 確認: 空の節は確認なしで削除する。空でない節は既定では確認モーダルを出すが、この確認の有無は個人設定（§4.4）で変更できる。削除は undo では戻せない（§8.6）。

8.1.3 複数行および ; を含むテキストペースト時の自動節分割〔状態: 実装完了〕

  • 節エディタへ既存のテキストを貼り付け（ペースト）した際、改行が失われることなく複数行のまま挿入される。
  • 貼り付けられたテキスト内に節区切り行（単独の ; 行）または場面見出し行（@A-B-C）が含まれている場合は、自動的にその位置で複数の節に分割して一括生成する。

8.3 原子的書き込み

環境 手順
デスクトップ 同一ディレクトリに .<name>.novnow-tmp を作成 → 全書き込み → fsync → rename（同一ボリューム内なので原子的） → 一時ファイル削除
Web files ストアへの readwrite トランザクション 1 回で put。トランザクション成功 = 保存成功

履歴ファイル（§13.2）だけはこの手順を使わず直接上書きする（一時ファイルもプロジェクト外には置けないため、§13.1.1）。

書き込み失敗（ディスクフル・権限・Quota 超過）時は SaveFailed へ遷移し、編集内容はメモリに保持したまま再試行する。 その間ステータスバーは赤で「閉じないでください」を表示し続ける（§8.4）。

    • Web: beforeunload で確認ダイアログ（Dirty/SaveFailed のときのみ登録、MUST）。

8.4.2 未保存ドット（オレンジ点）の視認サイズ〔状態: 実装完了〕

  • 文脈ビューおよびステータスバーで未保存（Dirty）状態を示す琥珀色（オレンジ）のドットは、一目で識別できる大きさ（直径 8〜10px 相当）で描画する。

8.5 外部変更との競合

  • プロジェクトディレクトリは 1,000ms 間隔でポーリング監視（v0 踏襲。inotify 等は使わない＝ Web と実装を揃えるため）。
  • 外部で変更されたファイルが Clean なら、カーソル位置を保ったまま再読込して I052 を出す。
  • Dirty のときは自動反映しない。ステータスバーに衝突インジケータを出し、Ctrl+Shift+D で差分モーダル（自分の版 / 外部の版 / 行単位マージ）を開く。
  • characters.md / words.md / materials/index.json の外部変更は常に即座に再読込（辞書は編集中バッファを持たないため）。

8.6 Undo / Redo

取り消しは 2 系統に分かれる。キーは同じで、ワークスペースの取り消しが効く状態ならそちらが先に消費し、 そうでなければ節エディタ（入力欄）の取り消しになる。IME の変換中はどちらも動かさない。

(a) 節エディタ内の文字編集

  • 単位は「節エディタ内の編集操作」。Ctrl+Z / Ctrl+Shift+Z（Ctrl+Y も可）。
  • 節をまたぐ undo は 行わない（混乱を避けるため、MUST）。
  • 自動保存は undo を妨げない（保存後も undo できる）。
  • 履歴は節ごとに保持する。節を移動するとその節の履歴は退避され、戻ってくると復元される （直近 20 節分。21 節目より古い節の履歴は捨てる）。
  • 履歴の深さ（1 つの節の中の取り消せる回数）は入力欄の実装の既定に従う（100 段）。
  • 節を消すと後続の節番号は繰り上がる（§8.1.2）ので、履歴は「文書・節 ID・節の開始行」に 紐づける。開始行が変わった節（＝前に別の節だった位置へ繰り上がった節）は履歴を引き継がない （消えた節の履歴で別の節の本文を戻してしまうのを防ぐ）。節の中で改行しても開始行は動かないので、 書き足している節の履歴は消えない。

(b) ワークスペースの取り消し（複数ファイルにまたがる操作）

  • 対象は「WorkspaceEdit として 1 回に複数の文書を書き換える操作」。プロジェクト全体の置換 （§9.7.4）、検索結果からの一括置換、agents/proposals/ からの採用がここに入る（MUST）。 1 回の apply を 1 単位とし、ファイルごとの変更前・変更後を 1 組として積む。
  • 深さは直近 100 操作。あふれたら古いものから捨てる。
  • 取り消し・やり直しは、積んだときの状態と今の状態が一致しているときだけ効く。対象の文書が 外部変更や他の編集で変わっていたら何もしない（上書きしない）。節エディタに未確定の入力が 残っているときも効かない。
  • 新しい操作を積むと、やり直しの側は捨てる。
  • 提案モード（§8.7）の間は効かない（提案の採用・却下は提案側の取り消しで扱う）。
  • 取り消し・やり直しの結果は未保存として扱い、通常の保存ステートマシン（§8.2）に乗る。

8.7 提案モード（人間用トラックチェンジ）

「元の文を消さずに別案を試す」ための編集モード。校正記号ではなく、AI 提案と同じ仕組みを人間に開放 したもの。

8.7.1 原理

novnow には既に「提案は本文を書き換えず agents/proposals/ に置く」という仕組みがある（委譲レベル propose の既定、原則 A2）。 提案モードは、人間の編集を同じ器に入れる だけである。新しい概念を作らない（P3）。

項目 内容
切替 Ctrl+Shift+P。ステータスバーに 提案 と表示され、エディタの左端に縦帯が出る
入力 通常どおり打つ。表示は即座に新しい文になる（打ちづらくならない）
保存先 本文ファイルは変更しない（MUST）。agents/proposals/H0044.md に差分として書く
ID H + 4 桁（Human）。エージェントの P#### とは別系列。採番は agents/proposals/ の走査で決める
通常モードに戻す 再度 Ctrl+Shift+P。提案は残り、本文は元のまま
採用 提案レビュー画面（§15.7.3）で「採用」。本文に書き込まれ、提案は applied になる
破棄 同画面で「破棄」。提案ファイルを削除する

8.7.2 agents/proposals/H0044.md の形式

target: @01-04-02-03
origin: human
status: open
created_at: 2026-10-09T21:40:12+09:00
updated_at: 2026-10-09T21:40:12+09:00
comment:
note: 語尾をもう少し硬くしてみる

## before
「……付き合ってあげるわよ」@リリア:B

## after
「……仕方ないわね。付き合うわ」@リリア:B
欄 意味
# H0044 提案 ID。GUI の提案モードは H + 4 桁、エージェントのツール核（section.propose / section.write など）は P + 4 桁。agents/proposals/ の同じ接頭辞の最大 + 1 を採る（接頭辞が違えば番号は独立）
kind human（GUI の提案モード）/ section-text / plot-field / idea / material / note。何を置き換える提案か
target 対象。contents/01-04.cnov @01-04-02-03（パス + 空白 + 節）またはプロットのパス
origin 作った経路。GUI の提案モードは human、エージェントのツール核を通るもの（MCP のツールと、そこへ委譲する正規操作 section.propose）は mcp、直接書き込み（section.write / plot.write）は mcp:<役割>
status open / accepted / rejected / superseded / applied
created_at / updated_at 作成・状態変更の時刻（RFC 3339）
comment 採用・却下の理由（人間が書く。空でよい）
note 提案時の一言（1 行に潰す）
partial true のときだけ出す。節の一部だけを置き換える提案（partial が無ければ節全体）

読み手は未知の欄を読み飛ばす（前方互換）。status が無いファイルは open として扱われない（提案一覧のバッジ・採用・却下の対象にならない）。

  • before は提案を始めた瞬間の節の全文（スナップショット）。
  • after は提案モードを抜けた時点の節の全文。
  • 節全体を持つ（行単位 diff にしない）。節は十分短く（既定 400 字目標）、 差分アルゴリズムを持ち込むと「どこが変わったか」の定義が曖昧になるため（MUST）。

8.7.3 表示

  • 提案のある節は、構成ツリーとエディタのミニヘッダーに 提案 n のバッジが出る。
  • 本文エディタ上に差分を重ねて表示しない（MUST）。赤取り消し線と緑追記を本文に重ねるのは P3 に真っ向から反するため。比較したいときは文脈ビュー（§9.4）を「before / after 並置」に切り替える。
  • 同一節に複数の提案（H0044 と H0045）を持てる。並置ビューでは Tab で切り替える。

8.7.4 制約

  • 提案モード中は 節を移動できる（移動すると、それまでの編集が 1 件の提案として確定する）。
  • 提案モード中の外部変更（§8.5）は、before との不一致として検出し W093 を出して提案を stale にする。
  • 提案は本文ではないので、文字数・進捗・統計の対象外（MUST）。
  • state: fixed の節にも提案は作れる（原則 A7 は propose レベルの エージェント の提案に関する既定であって、人間の試行は妨げない）。
