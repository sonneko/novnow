9.1.5 ヘッダの省略規則とプロジェクト名・パンくずのボタン

  • ヘッダの要素は、左から画面切替アイコン列・プロジェクト名・パンくず・切替直後の画面名（1 秒）・右端の常設ボタン（ヘルプ・パレット・テーマ・言語）の順に並ぶ。幅が足りないときは、画面名の一時表示 → プロジェクト名 → パンくずの順に省略し、画面切替アイコンと右端の常設ボタンは常に残す。プロジェクト名は末尾を省略し、ホバーで全文を表示する。
  • プロジェクト名はボタンであり、押すと Ctrl+O と同じ規則（現在の変更を保存してからプロジェクト選択画面へ戻る。保存に失敗している間は戻らず、その旨を知らせる）でプロジェクト選択画面へ戻る。
  • ヘッダのパンくずはボタンであり、押すと @ だけを入力した状態でコマンドパレットを開く。節エディタのミニヘッダー（§9.4.2）とステータスバー（§9.6）のパンくずは表示専用のままである。
  • どちらのボタンも押せる要素の統一表現（下線・ホバー背景・ポインタ、§9.1.4）に従う。パンくずを持たない画面ではパンくずボタンを出さない。

9.2 ラベル撤廃規則

9.2.1 規則

文字ラベルを置いてよいのは次の 3 つだけ（MUST）。

  1. 内容を見ても役割が分からない場合（例: 参照ペイン内の情報種別見出し）
  2. 破壊的操作（削除・却下・上書き）の確認
  3. 診断・エラー・ヘルプの文言

それ以外は アイコン・配置・色・フォーカスリング で表現する。

  • フォーカス中のペインは外周 2px の accent 枠。非フォーカスは枠なし。
  • 文字ラベルでペイン名を書かない。Ctrl+1/2/3 の対応は ?（ヘルプオーバーレイ）でのみ説明する。

9.2.4 編集面の左線

複数行のテキスト編集面には、左端に幅 3px の縦線を常時出す。普段は薄い色（accent.faint、§11.1）で「ここは編集できる場所である」ことを示し、フォーカス中は濃い青（accent）にする二段表示とする。対象は、節エディタ、話プロット・構成・配役・アイデア・資料本文の各エディタ、資料フォームの要約・条件欄、MCP 設定のコード欄、タスク作成の例欄である。1 行入力は対象にしない。

線の色の意味は、青 = 編集面とフォーカス、橙・緑・灰 = 状態（提案モードの警告線、節リストの状態色など）で分ける。同じ左端で両方が重なる場合は、警告・状態の表示を優先する。

9.3 文脈ビュー（メインカラム上段）

9.3.1 内容

現在の節を中心に、前 3 節・後 3 節（既定、ui.json の context_sections: 1..9）を読み取り専用で表示する。

  • 1 行の最大幅: 全角 44 字（既定）。これを超える幅があっても文字列は折り返す（指示 3「前後の節の表示幅を広げる」に対応し、v0 の狭いツリー併置をやめた分を使い切る）。
  • 本文フォント 15px / 行間 1.9 / 段落間 8px。
  • 節の境界には border 色の 1px 横線を引き、8px の余白と節番号の薄い表示（01-04-02-02 の 4 階層形式、fg.faint、10px、右寄せ） で示す。
  • 構文ハイライトは本文と同じ（§11.2）。役割語の緑下線もここで見える。
  • スクロールは常に「現在の節が画面の上から 38% の位置」に来るよう自動追従する。

  • 節境目の横線: 文脈ビューに並ぶ各節の境界に明確な横線を引き、節ごとの区切りを分かりやすくする。
  • 節番号表記の統一: 文脈ビューの節番号表示は、章番号を省略した B-C-D 形式ではなく、常に 4 階層すべてを含む **A-B-C-D（@AA-BB-CC-DD）**で統一表示する。
  • 編集中プレースホルダとフォーカス縦線の対表示: 文脈ビュー内の「現在編集中の節」のプレースホルダ左端にも 3px の縦線を表示し、節エディタ側のペインフォーカス縦線と対で見せる。
  • 未保存ドットの拡大: 節ごとの未保存状態を示すオレンジの点を視認しやすい大きさ（直径 8〜10px 相当）にする。
  • 本文 0 文字時の 3 行ガイド: 本文が 0 文字のときは、文脈ビュー領域に 3 行の操作ガイド（Alt+数字=画面 / Alt+矢印=節移動 / Ctrl+P=一覧）を薄字（fg.faint）で表示する。
  • 可視範囲のみのレイアウト: 文脈ビューはスクロール領域の可視範囲に入る節・行のみをレイアウトおよび描画する。

9.3.5 節の削除ボタン

文脈ビューの各節には、その節を指定して削除するボタンを置く。削除の意味と確認の規則は §8.1.2 に従う。節エディタのミニヘッダー（§9.4.2）には削除ボタンを置かない。

9.4 節エディタ（メインカラム下段）

9.4.1 基本

  • 編集対象: 現在の節のテキスト全体（複数行）。
  • 行番号: 節内のローカル行番号（1 始まり）を左に表示。ファイル全体の行番号は出さない（節が単位であるため）。
  • Enter は改行。Ctrl+Enter はカーソルのバイト位置で節を 2 つに分割する（§8.1.1）。節の末尾では「確定して次の節へ」と同じ結果になり、次が無ければ新規節を作る。
  • Ctrl+; は「この節の直後に新しい節を作って移動」。
  • ソフトラップ有り。横スクロールは発生させない。
  • 入力補完（§9.7.3）はこのペインでのみ動作する。

9.4.4 繰り返し・接続詞・多用の検出（W087 / W088 / W097–W106 の算法）

9.7.5 重ね物（モーダルと軽い重ね物）の共通規則

画面の上に重なる表示は、背面の操作を遮るモーダルと、遮らない軽い重ね物（検索/置換バー・入力補完・情報ポップアップ・クイックフィックス）に分ける。閉じ方と配置は全画面で次のとおり統一する（MUST）。

  • 閉じ方: モーダルは Esc またはモーダルの外側のクリックで閉じる。破壊的操作の確認モーダルでは、外側クリックは「キャンセル」と同じ意味とする。次の 2 つは外側クリックでも Esc でも閉じない（閉じると警告の意味が消えるため）: 保存失敗の通知、未保存の変更があるときの終了ガード。外側クリックが背面の要素を操作することは決してない。
  • 軽い重ね物: 外側クリックでは重ね物を閉じるだけとし、そのクリックを背面のボタンやエディタへの操作として通さない。
  • 配置: モーダルは画面中央に置く。コマンドパレットなどのパレット系は従来どおり画面上部に置く。
  • 閉じる案内の共通フッタ: 外側クリックと Esc で閉じられるモーダルには、末尾に「Esc / 外側クリックで閉じる」の案内を共通で出す（§9.2.1 の例外 3「ヘルプの文言」に当たる）。閉じられないモーダルには出さない。
  • 入力の下書き: 閉じたとき、改名・新規資料のタイトル・行幅設定・ジャンプ先のような短い 1 項目の入力は破棄する。項目の多いフォーム（MCP 設定・タスク作成・エクスポート設定・却下／差し戻しコメント・アイデア即時入力）の入力は、アプリを閉じるまでの間だけ保持し、次に開いたとき復元する。却下／差し戻しコメントは、同じ提案・同じ向きで開いた場合だけ復元する。下書きをファイルへ保存することはない。

9.7.6 最近使った項目

  • コマンドパレットの >（コマンド）と @（節移動）では、最近実行した項目をモードごとに直近 10 件まで覚える。同じ項目を再び実行したら先頭へ移す。
  • 履歴は、パレットを開いた直後の入力が空のときだけ候補の先頭に出す。文字を入力した後は §9.7.1 の固定スコアと ID 順に戻り、履歴は順位に影響しない（検索中の決定論を保つ）。
  • 履歴はアプリを閉じるまでのメモリ内にだけ持ち、ファイルへは書かない。ヘッドレスの候補生成には持ち込まない。

9.7.7 候補一覧のスクロール

  • 候補一覧を持つ重ね物（コマンドパレット・全体検索・資料検索・使用箇所一覧・昇格先選択）では、キーで選択を移したとき、選択行が見える位置までだけ一覧をスクロールさせる（最小移動。選択行を中央へ寄せたりはしない）。
  • 一覧のスクロールバーは重ね物の枠の右端に寄せて置き、普段は細く目立たせず、ホバーまたはスクロール操作のときに見える形にする。

9.7.8 パレットの配置・幅固定・ガイド・広さ優先 @ 移動・> 全コマンド化・? 選択・Tab 補完〔状態: 実装完了〕

  • 表示位置と最前面レイヤ（z-index）: パレットは画面水平方向の中央・上端（VS Code と同じ位置）に配置し、節エディタの枠線を含むすべての背面要素より前面（最上位レイヤ）に描画する。
  • 横幅固定と長文省略: パレットの横幅は固定とし、選択肢のテキストが長い場合は末尾を ... で省略（または短く整形）してパレット自体の幅や位置がズレないようにする。
  • 閉じる手段と外側クリック: 選択肢の中に「パレットを閉じる」を用意する。またパレットを開いている間にパレット外をクリックしたときは、背面の要素は押された判定にしないままパレットだけを閉じる。
  • 未入力時ガイドと 0 件表示: 未入力のパレットの下部に「> コマンド / @ 節 / ' 辞書 / M（#）資料 / ? ショートカット」のルール説明ガイドを表示する。また資料や一致項目が 0 件のときは空白にせず「一致する項目がありません（ない）」と明示表示する。
  • > コマンドの階層化と全ショートカット網羅:
    • > を押した初期状態ではエージェント関連の設定が大量に並んで他を埋めないよう、エージェント関連は >agent の親項目にまとめる。
    • すべてのキーボードショートカット操作を > パレット経由でも実行できるようにし、さらに agents/mcp.json の編集モーダルや初回ウェルカム案内も > から呼び出せるようにする。
  • ? によるショートカット選択実行: パレットの ? は単なる一覧表示ではなく、ショートカットを検索・選択してそのまま実行できるモードとする。
  • @ による広さ優先の階層移動: @ を用いた移動では、最初から @01-01-01-01, @01-01-01-02, ... と深さ優先で並べるのではなく、まず @01-* 〈第1章タイトル〉, @02-* 〈第2章タイトル〉, ... を提示し、選択または入力に応じて話（@01-01-* 〈話タイトル〉）→ 場面（@01-01-01-* 〈場面タイトル〉）→ 節（@01-01-01-01）へと広さ優先で段階的に掘り下げる。
  • 個別単位での Tab 補完: パレット入力中に Tab キーを押すことで、個別のトークン単位（例: ">ag" → ">agent "、"@01" → "@01-"）で入力を補完できる。

9.8.4 衝突の確認

Ctrl+1..3（ペイン）と Alt+1..9（ワークスペース）と Ctrl+Shift+1..9（節維持切替）は衝突しない。 agent ワークスペースの 1〜4（委譲レベル変更、§15.7.6）と Ctrl+Shift+X（総停止、§15.7.4）も、 修飾キーの有無でこれらと区別できるため衝突しない（MUST）。

Alt+← / Alt+→ の二重割当（解決規則、MUST）: 既定は「前/次の場面へ」（§9.8.2）。 句切れ提案レイヤー（§9.4.3）が 有効 かつ 現在の節に候補が 1 件以上ある ときのみ、候補移動が優先される。 候補が尽きた状態でさらに押すと、場面移動に戻る。レイヤーが無効なら常に場面移動。

IME 変換中（composing）はすべてのショートカットを無効化する（MUST、実装規約は §9.8.5）。Alt 系は macOS では Option が文字入力に使われるため、macOS では Ctrl+Alt に読み替える（MUST）。 Ctrl+K Ctrl+0 は 2 ストローク（Ctrl+K を押してから 2 秒以内に Ctrl+0）。2 秒を過ぎたら破棄する。 Ctrl+0（文字サイズ既定）とは、直前に Ctrl+K があったかどうかだけで区別する。

9.8.5 IME 変換状態とフェイルセーフ規則（MUST）

  1. 変換開始・更新・確定の追跡: IME の変換開始（CompositionStart）および変換更新（CompositionUpdate）で「変換中」状態に入り、変換確定またはキャンセル（CompositionEnd）で「変換中」状態を解除する。
  2. 変換中のキーイベント抑止（MUST）: 「変換中」状態の間は、すべてのキーボードショートカット（§9.8.1〜§9.8.3）、Enter による節確定（§9.4）、および Esc によるモーダル閉じ（§9.6）を抑止する。変換候補の選択・確定・取消に使われるキーがエディタやシェルの操作として誤発火してはならない。
  3. フェイルセーフ解除（MUST）: OS やブラウザによっては変換取消時に終了イベントが届かない場合があるため、以下のいずれかで「変換中」状態を自動的に解除する。
    • ウィンドウがフォーカスを失ったとき。
    • 最後の変換イベントから 2 秒 が経過し、かつその間にテキスト入力もキー入力も発生していないとき。
  4. 変換候補ウィンドウの位置（MUST）: 編集領域にフォーカスがある間、常に現在のキャレット矩形を OS / ブラウザの IME へ通知し、変換候補ウィンドウがキャレット直下に表示されるようにする。

9.8.6 キー割当の統一とブラウザ・OS 非衝突化〔状態: 実装完了〕

  • ブラウザ・OS 予約キーとの非衝突化: ブラウザや OS に奪われやすいショートカットには競合しない代替キーおよび画面上のボタン・パレット実行経路を用意する。 Web で Ctrl+Shift+I（開発者ツール）、Ctrl+Shift+N（シークレットウィンドウ）、Ctrl+Shift+T（タブ復元）、Ctrl+Shift+W（ウィンドウを閉じる）が優先される環境では、それぞれ Ctrl+Alt+Shift+I/N/T/W を代替キーとして使える。
  • 一覧移動と確定移動の統一: 全ワークスペースで「一覧・タイムラインの選択移動は素の ↑ / ↓、編集を確定して前後へ移動は Alt+↑ / Alt+↓」に統一する。素の ↑ / ↓ はエディタにフォーカスがあるときだけエディタが受け取り、それ以外のときはどの画面でも一覧・タイムラインに効かせる。
  • Ctrl+3 と Tab の役割統一: Ctrl+3 は全画面共通で「参照ペインへフォーカス」の 1 つの意味に統一し、資料ワークスペース内の審査・メタデータフォーム等へのフォーカス移動は Tab / Shift+Tab に移す。
  • Ctrl+O の挙動統一: デスクトップ版と Web 版の双方で、Ctrl+O は「現在の変更を保存してからプロジェクト選択画面（一覧・履歴）へ戻る」に統一し、一覧画面から「フォルダを開く」で選択する 2 段構成にする。

9.8.7 キー案内のクリック実行

  • ヘルプ（?）のキー一覧と、各画面の末尾に出るキー案内は、項目ごとに押せるボタンとして並べる。押すとそのキー操作をそのまま実行する。対象はこの 2 か所の案内だけであり、ホバーのツールチップやステータスバーの補完表示（§9.6）は押せるようにしない。
  • 破壊的・確認付きの操作を案内から実行するときも、通常の確認経路をそのまま通る。ヘルプの中の項目を押したときは、ヘルプを閉じてから実行する。
  • 案内の文言は項目単位に持ち、実際のキー割当（本節）と食い違わないことを機械的に検証できる形にする。

9.9 アクセシビリティ

  • すべてのインタラクティブ要素は Tab 順に並び、OS の支援技術（アクセシビリティツリー）へ公開する（SHOULD）。
  • アイコンのみの要素にはアクセシブル名（i18n 済み）を必ず付ける（MUST）。文字ラベルを消すことと、支援技術への情報提供は両立させる。
  • 色だけで情報を伝えない: 保存状態は色 + 形、診断は色 + 波線形状 + レビュー一覧のテキスト。
  • 最小コントラスト比 4.5:1（本文）/ 3:1（12px 以上の補助テキストと図形）。

9.9.2 クリック対象のホバー変化・下線・24×24px 以上の当たり判定保証〔状態: 実装完了〕

  • すべてのクリック対象（ボタン、一覧行、タブ、カテゴリチップ、クイックフィックス候補、ヘッダアイコン等）について、次の 3 条件を必須とし自動テストで検証する:
    1. 押せる要素には共通して薄い黒（または前景色）の下線を入れる。
    2. ホバー時に背景色（bg.selection の 60%）とポインタカーソルへの変更を付ける。
    3. 見た目の描画寸法は変えずに、クリックの当たり判定矩形だけを 24×24px 以上（WCAG 2.5.8 基準）へ広げる。

10.0 切替の挙動

ワークスペースは「同じ場所を違う視点で見る」ための装置であり、切替は思考を途切れさせてはならない。

項目 規則（MUST）
Alt+1..9 ワークスペースを切り替える。SceneId は維持。各ワークスペースが最後に居たスクロール位置・フォーカス位置を復元する
Ctrl+Shift+1..9 節位置を強制的に持ち越す。切替先が最後に居た場所ではなく、今いる節の対応物 に着地する
切替の所要時間 16ms 以内（1 フレーム）に描画が完了すること。ローディング表示・フェード・スライドを 出してはならない
事前計算 切替先の状態は常にメモリ上に保持する。ワークスペースの破棄・再構築をしない
未保存 切替は保存のトリガーになる（§8.2 の「節位置変更」と同じ扱い）。確認ダイアログは出さない
Alt+Tab 相当 Ctrl+Tab は ファイル の循環であってワークスペースではない。ワークスペースの「直前に戻る」は Alt+0

項目 定義（MUST）

12. 国際化

12.1 対象言語

ja（日本語）と en（English）の 2 言語を 同等にサポート（MUST）。どちらかが「翻訳の劣化版」になってはならない。

12.2 ドメイン処理と表示文言の分離（MUST）

  • ドメイン処理はユーザー向けの表示文言を直接持たず、診断コードと構造化引数のみを生成する。
  • 表示文言への展開はすべて選択中の言語（ja / en）の文言カタログによって行う。
  • CLI のメッセージも同じ文言カタログを使用する（§14.2）。
  • 字句データは表示文言に含まない: ファイル形式の語彙・記号（§5.0.2 のシジル文字 「」、§5.0.6 のフィールドキー日本語別名など）は UI 言語に依存せず（§12.6「UI 言語が en でも受理する」）、どの言語設定でも同一に解釈する。

12.3 カタログ

  • 形式: 日本語（ja）と英語（en）の 2 つの文言カタログで管理する。
  • キー命名: <領域>.<対象>.<語>。例: status.unsaved, palette.hint.command, diag.E004, cli.error.incomplete.
  • プレースホルダ: {0}, {1}（位置引数のみ。名前付きは使わない）。
  • 整合条件（MUST）: 2 つのカタログのキー集合および各キーのプレースホルダ番号集合は完全に一致しなければならない。
  • 欠落時のフォールバック: en → キー文字列そのもの、の順にフォールバックする。

12.3.1 日本語テンプレート直後の助詞空白規則〔状態: 実装完了〕

  • 日本語（ja）の文言では、{0}はこの版ではまだ使えません のように、プレースホルダ {0} 等の直後に助詞（「は」「が」「を」「に」「へ」「で」「と」「の」「も」等）が続くときは半角空白を入れない。この規則は自動テストで検査する。

12.4 言語の決定順序

  1. .novnow/ui.json の language（ja / en）
  2. NOVNOW_LANG 環境変数（CLI でも GUI でも有効）
  3. OS / ブラウザのロケール（ja* → ja、それ以外 → en）
  4. 既定 ja

  • プロジェクトの中身（本文・プロット・キャラ・資料・アイデア・プロンプト）は 決して自動翻訳しない（MUST）。
