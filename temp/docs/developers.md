# 開発者ガイド（Developers Guide）

本書は本プロジェクトの開発に参加する人間および AI エージェント向けの固定情報をまとめる。現在の進捗や直近の作業状態は `REF:docs/handoff.md`、一時的な計画は `REF:docs/plans.md`、過去の意思決定やマイルストーン履歴は `REF:docs/history.md` を参照すること。

---

## 1. ドキュメント管理規則（必読・削除禁止）

以下のブロックはユーザーから指示されたドキュメント管理規則の原文であり、明示的な削除指示がない限り一字一句変更・削除してはならない。

```text
1. ドキュメント整理
ドキュメントが肥大化してきたため、整理を行う。「最初はXだったが、Yに変更した」のような歴史的情報は読む際のノイズになるため、現行の仕様や設計からは分離し、`docs/history.md` に移動する。この際、`docs/history.md` は先頭から全文を読まなくても `grep` 等で機械的に該当箇所を特定できる構造にすること。

docs/
├ script/ : ドキュメントのルールが守られているか確認するスクリプト群（`verify-docs.py` を含む）
├ handoff.md : 開発を始めるにあたって必要な最小限の流動的情報（現在の進捗など）。毎セッション更新する
├ specifications/
│ └ **.md : 複数のマークダウンファイルに分類された純粋な仕様書（ユーザーから見える仕様のみを記述する）
├ designs/
│ └ **.md : 複数のマークダウンファイルに分類されたコードの設計書（ファイル構成や章立ては `specifications` と完全に一致させる）
├ plans.md : 一時的な計画や方針、途中の履歴などを記述するファイル（マイルストーン達成時に `history.md` へ移動する）
├ developers.md : 開発環境の構築手順、このプロンプトで指示しているドキュメント管理ルール、ソースコードのディレクトリ構造、スクリプトの使い方、ユーザーの開発の進め方、ArenaAgentの仕様、その他仕様外の注意点など、開発開始時に必要な固定情報
└ history.md : 変更履歴や過去の経緯などを記録するファイル（追記専用）

ドキュメント管理のルールは以下の通りとする。
・複数のドキュメントに重複した情報を記述しない。ただし、実装状況などどうしても重複が避けられない情報については、`docs/script/verify-docs.py` によって機械的（決定論的）に内容の同一性が検証されている場合に限り許容する。
・矛盾が生じた場合の優先順位は「`specifications/**.md` > `designs/**.md` > ソースコード」とする。例えば、仕様書にない機能が実装されている場合は、仕様書の記述漏れか不要な実装である可能性を疑う。逆に仕様書にある機能が実装されていない場合は、単に未実装であるか、仕様変更の反映漏れの可能性がある。なお、仕様書や設計書を修正する際は、単なる記述ミスの修正を除き、人間の承認を得ること。
・`specifications/**.md` にはコードに関する情報を一切含めず、純粋な仕様のみを記述する。また、他のファイルへの参照も一切含めない。
・`designs/**.md` の構造は `specifications/**.md` と一致させる。例えば、`specifications/A.md` のB章に対応する実装は、`designs/A.md` のB章に記述する。また、各章には実装状況（実装待ち / 実装中 / 実装完了：（関連するソースコードへの参照必須））を記録する。
・他ファイルへの参照は `specifications/**.md` 以外では積極的に行ってよい。ただし、機械的に管理できるよう、すべての参照には `REF` プレフィックスを付与するなどの工夫を行うこと。
・ここで指示したドキュメント管理ルール自体も `docs/developers.md` にそのまま記載し、明示的な削除指示がない限り削除しないこと。
```

### 1.1 `REF:` 参照記法と同期ブロックの規約

1. **ファイル参照（`REF:`）**:
   - `docs/specifications/**.md` 以外のドキュメントからリポジトリ内のファイルを参照するときは、必ず `` `REF:<相対パス>` `` または `` `REF:<相対パス>#<アンカー>` `` の形式で記述する（例: `REF:src/...`, `REF:docs/plans.md#m0-setup`）。
   - `docs/designs/**.md` の各 `### ` 節の冒頭には、必ず次のいずれかの形式で実装状態を 1 行で記載する。
     - `状態: 実装完了（REF:src/...）`
     - `状態: 実装中（REF:src/...）`
     - `状態: 未実装・実装計画済み（REF:src/..., REF:docs/plans.md#...）`
     - `状態: 未実装・未計画（REF:docs/plans.md#unplanned）`
     - `状態: 実装待ち`
2. **重複許可ブロック（`SYNC` マーカー）**:
   - `REF:docs/handoff.md` と `REF:docs/plans.md` の間で共有するマイルストーン達成状況など、重複が避けられない箇所は `<!-- SYNC:START <id> -->` と `<!-- SYNC:END <id> -->` で囲み、`REF:docs/script/verify-docs.py` でバイト単位の一致を検証する。
3. **仕様書と設計書の対応**:
   - `docs/specifications/<name>.md` と `docs/designs/<name>.md` は `## ` および `### ` 見出しを完全一致させる。

### 2.2 Arena サンドボックス環境でのツールチェーン復旧

Arena サンドボックスには初期状態で目的のツールチェーンが入っていない場合がある。外部通信が制限されているため、以下の手順でツールチェーンを展開する。

1. **ツールチェーンの展開**:
   ```bash
   bash scripts/bootstrap-toolchain.sh
   ```
   詳細は `REF:scripts/bootstrap-toolchain.sh` を参照。
2. **各コマンド実行時の環境有効化**:
   `bash` ツール呼び出しは毎回新しいシェルで起動するため、コマンドを実行する際は必ず先頭に環境有効化コマンドを付ける。
   ```bash
   . /home/user/build/env.sh && <コマンド>
   ```

## 4. スクリプトの使い方

### 4.1 `bash scripts/verify.sh`（コミット前の必須検証）

コミット・プッシュ前に必ず実行し、すべて通ることを確認する。

1. `python3 docs/script/verify-docs.py`（ドキュメント規則・重複・`REF:` リンク検査）
2. 言語固有の静的解析・フォーマットチェック
3. テストの実行

### 4.2 `python3 docs/script/verify-docs.py`（ドキュメント規則検査）

ドキュメントのみを編集した際にも単体で高速に実行できる。終了コード `0` で全規則合格、非 `0` で違反箇所を標準エラーに出力する。

### 4.3 Arena サンドボックス環境での所要時間目安

`bash` ツールの `timeout` 設定（デフォルト 30s、最大 1800s）を決める際の目安として、各コマンドの初回・2 回目以降の所要時間を `docs/handoff.md` に記録しておくこと。

## 5. ユーザーの開発の進め方（作業の作法）

1. **ブランチと PR の運用**：
   - セッションに紐づく専用作業ブランチ（`arena/...`）でのみ作業し、別ブランチの作成や切り替えは行わない。
   - **作業の区切りごとにこまめにコミット & プッシュ**する。
   - PR の作成・更新はエージェントが行うが、**PR のマージは必ずユーザー自身が行う**（エージェントが勝手に `gh pr merge` を実行してはならない）。
   - 作業完了時は PR が Ready for review であること、コンフリクトがないこと、GitHub Actions の全チェックが green であることを確認してから報告する。
2. **自律判断と人間承認の境界**：
   - 仕様書（`docs/specifications/**.md`）および設計書（`docs/designs/**.md`）で既に決まっている事項の実装・テスト・バグ修正は確認を求めず自律的に進める。
   - 仕様書や設計書の内容自体を変更する場合は、単なる記述ミスの修正を除き、人間の承認を得ること。

## 6. Arena Agent の仕様と環境上の制約

1. **通信ホワイトリスト**：
   - サンドボックスから外部通信が可能なホストは `github.com`, `codeload.github.com`, `api.github.com`, `registry.npmjs.org`, `pypi.org`, `files.pythonhosted.org` の 6 つに限定される。
   - 公式配布元（各種レジストリ、GitHub Releases のアセット等）には直接到達できないため、新しい依存やバイナリがどうしても必要な場合は GitHub Actions ワークフロー経由で取得し、Git Blob や専用ブランチに退避する。詳細は `REF:docs/add-dependencies.md` を参照。
2. **コンテナ再起動とスナップショットの挙動**：
   - セッションが長くなるとターン間でサンドボックスのコンテナが再起動することがある。
   - スナップショットで永続化されるのはリポジトリの作業ツリー配下のみであり、除外ディレクトリ（`target/`, `dist/`, `build/`, `node_modules/`, `.cache/` 等）および `/home/user/build/` は消える。
   - コンテナ再起動時は `.git/refs/heads/...` が古い状態に戻ることがあるため、必ず次の手順で復旧する：
     ```bash
     bash scripts/bootstrap-toolchain.sh
     git fetch origin <現在のブランチ名>
     git reset --mixed FETCH_HEAD
     ```
3. **パッチセット上限（128MB / 10,000 ファイル）**：
   - ターン終了時の累積成果物スナップショットには約 128MB または 10,000 ファイルの上限がある。大きな一時ファイルや成果物は必ず `/home/user/build/` または `/tmp/`、もしくは除外ディレクトリ名（`target/`, `dist/` 等）の下に置き、リポジトリ内の追跡対象外パスに放置しない。
4. **GitHub CLI（`gh`）での PR 更新**：
   - `gh pr edit` は GitHub 側の Classic Projects 廃止エラーで失敗することがあるため、PR のタイトルや本文を更新する際は REST API を直接呼ぶ：
     ```bash
     gh api repos/<owner>/<repo>/pulls/<PR番号> -X PATCH --input - <<'JSON'
     {"title": "...", "body": "..."}
     JSON
     ```

## 7. テスト戦略

<!-- プロジェクトに合わせて適宜書き換える -->

テストは以下の層で検証する：

1. **アーキテクチャ・不変条件検査**: コードの層構造や禁止パターンを AST 走査等で検査
2. **仕様書直結の契約テスト**: 仕様書の記述とコードの動作が一致することを検証
3. **統合テスト**: 機能単位のエンドツーエンド検証
4. **E2Eテスト**: 実際の環境での動作検証

### 7.1 テストの運用規則

- テストフィクスチャは**手書き・手動編集を禁止**し、必ずテストコードの確定ロジックから生成した出力を人間が diff レビューした上でコミットする。
- 既存の期待出力の差分が発生した場合は退行バグとして扱う。

## 8. 仕様外の注意点（技術的な落とし穴一覧）

これまでの開発で実際に遭遇した落とし穴と対処法を領域別に記録する。新しい問題に遭遇した場合はここに追記すること。

### 8.1 一般的な注意事項

1. **ビルドツールのバージョン差異**: CI とローカルでバージョンが異なる場合は挙動差に注意
2. **ファイルパスの大小文字**: ファイルシステムにより大小文字の扱いが異なる
3. **改行コード**: 改行コードの差異（CRLF vs LF）によるテスト失敗に注意
